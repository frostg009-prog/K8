# Аудит возможности установки сторонней прошивки — плата K8

> Цель документа: не «взлом» чужого устройства, а оценка **собственной** платы —
> можно ли легитимно запускать на ней свой код / свою прошивку, и как это проверить.
> Исходников прошивки в репозитории нет, поэтому это методология + разбор по интерфейсу.

## 1. Что это за устройство (по интерфейсу)

На плате **два независимых вычислителя**, и это ключевой факт:

| Что видно в UI | Что это на самом деле | Версия |
|---|---|---|
| `System Version S1.0`, веб на `192.168.32.1:8080`, ночное видение, Ground Tracking, CAM2 | **SOC** — система-на-кристалле под Linux (камера, ИИ-трекинг, сеть) | S1.0 |
| `APP Version GS2.0.3`, каналы CH7–CH12, Smart Assisted Lock, Precision Crosshair Lock | **FC / MCU** — полётный контроллер (микроконтроллер) | GS2.0.3 |

Подключение для обслуживания: **порт SOC → USB → ПК**, затем веб-интерфейс
`http://192.168.32.1:8080/`, вкладка **Sys**, блок **Update → Offline package →
Choose File → Start Upgrade**.

Вывод: «своя прошивка» — это **две разные задачи** (SOC-образ и FC-прошивка), с разными
механизмами защиты. Оценивать надо каждую отдельно.

## 2. Главный вопрос всего аудита

Можно ли залить свой код, определяется **ровно одним** свойством канала обновления:

> **Проверяет ли загрузчик/апдейтер криптографическую подпись пакета обновления?**

- **Нет подписи (только CRC/контрольная сумма или открытый формат)** → перепаковываешь
  официальный пакет со своим содержимым, и он загружается. Своя прошивка **возможна**.
- **Есть подпись, ключ у вендора, Secure Boot прошит** → штатно залить произвольный код
  **нельзя**; остаются только уязвимости загрузчика/цепочки — это уже не «штатная
  установка», и для своего устройства обычно проще искать документированный дебаг-доступ.

Всё остальное ниже — как это выяснить на практике.

## 3. Методология: пошаговая разведка

### Шаг 0. Снять бэкап и зафиксировать «как было»
Перед любыми экспериментами: сохранить текущий официальный пакет обновления, версии,
по возможности дамп флеша. Чтобы можно было вернуть устройство в исходное состояние
(защита от «кирпича»).

### Шаг 1. Сеть и сервисы SOC
SOC поднимает Linux + веб-сервер. Это самая «открытая» часть.
```bash
# что слушает устройство
nmap -sS -sV -p- 192.168.32.1

# типичные находки на таких платах:
#  22/tcp   ssh      -> прямой шелл, если включён
#  23/tcp   telnet   -> часто открыт с завода, иногда без пароля
#  8080/tcp http     -> веб-апдейтер (виден в UI)
#  adb     -> если SOC на Android/AOSP-подобной сборке
```
- Есть `adb`? → `adb devices && adb shell` часто даёт root на таких трекинг-платах.
- Открыт telnet/ssh с дефолтными кредами? → сразу получаешь систему SOC.
- Если зашёл в Linux — ты уже «владеешь» SOC-стороной: можно подменять бинарники
  трекинга, свои скрипты запуска и т.д. Это и есть «своя прошивка» для SOC де-факто.

### Шаг 2. Разобрать пакет обновления (самое важное)
Берёшь официальный offline-пакет (тот, что грузится через Choose File) и смотришь, что он
из себя представляет:
```bash
file update.bin          # тип: архив? образ? сырой бинарь?
binwalk -Me update.bin   # извлечь вложенные ФС/образы/подписи
strings update.bin | grep -iE 'sig|rsa|sha|cert|key|version|magic'
xxd update.bin | head     # magic-заголовок, структура
```
Что ищешь:
- **Подпись/сертификат** (блоки RSA/ECDSA, X.509, `*.sig`) — значит, проверка подписи
  скорее всего есть.
- **Только CRC32/MD5/SHA без подписи** — целостность есть, аутентичности нет: пакет можно
  пересобрать. Своя прошивка реальна.
- **Открытые squashfs/ext/cpio внутри** — структуру образа видно, можно собрать свой.

### Шаг 3. Как апдейтер проверяет пакет
Сам процесс проверки живёт в скрипте/бинаре апдейтера на SOC (который обслуживает
`:8080`). Если на Шаге 1 получил шелл:
```bash
# найти логику обновления
grep -rIl -iE 'upgrade|update|verify|signature|openssl' / 2>/dev/null
# типичные места: /usr/bin, /opt, веб-корень сервиса :8080, /etc/init.d
```
Если в коде проверки видно `openssl dgst -verify` / сравнение с вшитым публичным ключом —
подпись есть. Если видно только `md5sum`/`crc` и распаковку — подписи нет.

### Шаг 4. FC / MCU (полётная часть, GS2.0.3)
Отдельная цель. Обычно это STM32/аналог. Критичны два момента:
- **Debug-порт (SWD/JTAG):** если выведен и не закрыт — можно читать/шить MCU напрямую
  (`openocd`, `st-link`). Это самый чистый путь к своей FC-прошивке.
- **Read-out protection (RDP на STM32 и аналоги):** если установлен RDP level 2 — чтение
  и отладка заблокированы на заводе. Тогда штатно свою прошивку в MCU не зальёшь.
- Как FC обновляется: часто SOC по UART прошивает MCU во время «Start Upgrade». Значит
  формат FC-прошивки и наличие её подписи тоже смотрятся внутри пакета из Шага 2.

### Шаг 5. Secure Boot / аппаратный корень доверия (SOC)
Даже если образ SOC без подписи на уровне апдейтера, у SoC может быть прошитый в eFuse
Secure Boot (Rockchip/Allwinner/Amlogic и т.п. это умеют). Проверка:
- загрузочный лог по UART-консоли платы (ищешь `secure boot`, `verify`, `fail`);
- документация на конкретный SoC (определить по маркировке чипа или по `cat /proc/cpuinfo`
  после получения шелла).

## 4. Дерево решений: возможна ли своя прошивка

```
Пакет обновления подписан?
├─ НЕТ  → перепаковать официальный пакет → Start Upgrade → СВОЯ ПРОШИВКА ВОЗМОЖНА
└─ ДА   → Secure Boot / RDP включены?
          ├─ НЕТ → доступ через debug-порт (SWD/JTAG) или шелл SOC → ВОЗМОЖНА (не через апдейтер)
          └─ ДА  → штатных путей нет; только уязвимости загрузчика → ПРАКТИЧЕСКИ ЗАКРЫТО
```

Параллельно для SOC-стороны: **если получен root-шелл (telnet/ssh/adb)** — ты уже можешь
запускать свой код на SOC независимо от подписи пакета. Для многих целей (свой трекинг,
свои алгоритмы на камере) этого достаточно, полная замена образа не нужна.

## 5. Чек-лист аудита

- [ ] Снят бэкап официального пакета обновления и версий (S1.0 / GS2.0.3)
- [ ] `nmap` по `192.168.32.1`: найдены открытые сервисы (ssh/telnet/adb/http)
- [ ] Проверены дефолтные/пустые пароли на telnet/ssh, доступ по adb
- [ ] Пакет обновления разобран `binwalk`/`strings`/`file`
- [ ] Найден (или не найден) блок подписи в пакете
- [ ] Прочитана логика проверки в апдейтере на SOC
- [ ] Найден и проверен debug-порт FC (SWD/JTAG), статус RDP
- [ ] Прочитан загрузочный лог по UART, определён статус Secure Boot
- [ ] Определён SoC по маркировке/`/proc/cpuinfo`, изучена его модель защиты
- [ ] Заполнено дерево решений → вывод по SOC и по FC отдельно

## 6. Риски

- **«Кирпич».** Неверный образ SOC или FC может сделать плату незагружаемой. Поэтому Шаг 0
  (бэкап) и желательно заранее найти путь восстановления (recovery-режим SoC, заводской
  UART-boot, внешний программатор флеша).
- **Гарантия и безопасность полётов.** Своя прошивка FC = полная ответственность за
  управление аппаратом. Тестировать только безопасно (без пропеллеров / на стенде).
- **Это оценка собственного устройства.** Методика — про право запускать свой код на своём
  железе, а не про обход защит на чужих устройствах.

## 7. Краткий вывод

По одному интерфейсу финально сказать «да/нет» нельзя — решает **Шаг 2 (есть ли подпись у
offline-пакета)** и **Шаг 1 (есть ли шелл на SOC)**. Самый быстрый практический тест:
1. `nmap` устройства и попытка telnet/ssh/adb — если зашёл, SOC-сторона открыта;
2. `binwalk` официального пакета — если подписи нет, апдейтер зальёт твою сборку.
Если оба закрыты (подпись + Secure Boot + RDP) — штатной установки своей прошивки нет.
